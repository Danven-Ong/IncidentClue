# Synthetic diagnostic CLI pilot — 28 October 2026

Three synthetic inputs were run once each through the installed diagnostic CLI with Groq's `openai/gpt-oss-20b`. All three returned accepted diagnoses and exit code 0. The observed statuses matched the evaluator's expectations. This small, manually reviewed pilot is not an accuracy benchmark, a reliability estimate, or proof of general prompt-injection resistance. Independent human review is pending.

## Method

The CLI implementation was unchanged from commit `b0c88e8b537457ebd7fd1e7a64dc4d54afe5c975`; new fixtures and evaluation files were uncommitted during execution. Each command loaded only its specified incident JSON and explicit local configuration. [Evaluator-only expectations](../../evals/pilot-cases.json) were written before inference and were not sent to the model. No prompt changes, response repairs, or retries were made for this pilot. All three attempts are preserved.

From the repository root in Git Bash, substitute the input filename for each case:

```bash
./.venv/Scripts/incidentclue.exe diagnose data/synthetic/checkout-ambiguous.json --env-file .env --record-dir runs
```

Inputs: [clear](../../data/synthetic/checkout.json), [ambiguous](../../data/synthetic/checkout-ambiguous.json), and [insufficient](../../data/synthetic/checkout-insufficient.json). Records include model/configuration, normalized input and instruction hashes, processing durations, accepted results, and source context. Hashes and citation membership were checked against each input after execution. Provider response identifiers and token usage were not exposed by the current diagnosis function and remain null. Processing duration includes local validation but excludes record writing; it is not pure provider latency.

## Limitations found

- The clear response leaves `missing_evidence` empty even though the upstream reason for the missing variable is unknown. It also suggests restarting the service. This is advice only; the application executed no checks or remediation. A restart should require operational judgment and authorization, and is outside a future read-only tool's scope.
- The ambiguous response mentions payment, inventory, and catalog as possible downstream services. The input provides no dependency inventory. Some wording presents these as examples; the next-check list should state that the operator must first identify actual dependencies. These names must not be treated as observed topology.
- The insufficient response includes network/DNS checks despite having no supporting observations. These are possible investigation directions, not evidence of a network/DNS cause; their priority cannot be established from this input.
- A schema-valid result with existing citation IDs can still make unsupported claims. Status matching is only one check. This review considered probable cause, citation support, missing information, and suggested checks separately.
- One run per case does not measure variability, accuracy on production incidents, repeated abstention behavior, cost, or adversarial robustness. Case expectations reflect deliberately constructed evidence and are not independently established production root-cause labels.

The pilot supports a working CLI demonstration with explicit abstention on these two uncertain inputs. Human review and an explanation of the request/validation flow remain before declaring the feature ready for merge. Improvements to suggestion wording and additional failure/adversarial cases can be evaluated separately; the raw results above were not rewritten to hide weaknesses.
